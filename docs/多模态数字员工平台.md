# 多模态数字员工平台
## 需求与设计文档


## 一、项目概述

### 1.1 项目定位

**项目名称**：MDE-LAB｜多模态数字员工平台（IT服务台方向）

**一句话定位**：一个以企业IT服务台为业务场景，用真实技术栈承载CrewAI多Agent协作、MCP协议、RAG知识库、多模态感知和人机协同的**演示项目**——由讲师面向**学员**演示数字员工如何工作，学员是演示的**观察者与操作者**，不是系统内的业务角色。

**核心原则**：
- **演示导向**：功能取舍以“能否讲清一个技术点”为准，不做教务/教学管理类功能（无教师、学生角色，无任务下发与评分）
- **真实业务逻辑**：按真实企业IT服务台的业务规则开发，会话、工单、转人工的流程与状态流转贴合实际，不做“演示特供”的假流程
- **简化但完整**：只保留一个外部系统（工单系统），用MCP协议对接，其余模块全部内置
- **真实技术栈**：CrewAI、MCP、RAG、ASR/TTS均为真实运行，非Mock
- **完整闭环**：用户提问 → AI理解 → 工具调用 → 回复 → 转人工 → 回归AI
- **多角色协作**：业务侧仅有用户、坐席、管理员三种角色，前端分角色设计，完整演示人机协同

### 1.2 教学价值

| 教学维度 | 覆盖能力 |
|---|---|
| 多Agent协作 | CrewAI角色化Agent定义、任务编排、协作流程 |

| RAG | 文档/图片解析、**多模态文本优先嵌入**、向量检索、精排、置信度护栏、图文生成与来源引用 |
| 多模态 | ASR语音识别、OCR图像识别、视觉理解、情绪识别、TTS、图片回复、参考来源展示 |

| 认证与权限 | 用户管理、角色管理、Token认证、权限矩阵 |
| 前端工程 | 分角色前端、路由守卫、WebSocket实时通信 |
| 工程实践 | FastAPI、WebSocket、SQLite、Docker Compose |

### 1.3 框架选型说明

| 维度 | CrewAI | LangGraph | 选型理由 |
|---|---|---|---|
| 核心理念 | 角色化Agent团队 | 状态图工作流 | 客服场景天然适合角色分工 |
| 学习曲线 | 低（角色-任务-团队） | 中（节点-边-状态） | 教学项目优先降低抽象负担 |
| 协作模式 | 内置委派与协作 | 需手动编排 | CrewAI更适合讲“多Agent团队” |
| 适用场景 | 角色分工明确的协作 | 复杂条件分支工作流 | 客服主流程以分工为主 |
| 参考案例 | IBM客服分析、Zendesk集成 | 复杂长流程 | 客服领域CrewAI案例更丰富 |

**结论**：教学项目选择CrewAI为主框架，对于复杂的条件分支（如转人工路由），使用CrewAI Flows（事件驱动编排）处理，降低理解成本。


## 二、业务背景与核心痛点

### 2.1 业务背景

企业IT服务台每天收到大量重复性咨询：VPN连接失败、密码重置、软件安装权限申请、报销系统报错等。这些工单占据了服务团队大量精力，却很少需要真正的专业判断。

### 2.2 核心痛点

| 痛点 | 描述 |
|---|---|
| 响应滞后 | 人工客服无法7×24小时即时响应 |
| 知识碎片化 | 信息分散在多个文档和系统中，查找困难 |
| 重复劳动 | 大量标准化问题消耗工程师时间 |
| 口径不统一 | 不同客服对同一问题的回答存在差异 |

### 2.3 核心价值

让AI数字员工接管80%以上的标准化IT咨询，实现“即时解决”，复杂问题无缝转交人工并附带完整上下文。

## 四、CrewAI Agent设计

### 4.1 Agent角色定义

基于CrewAI的角色化团队模式，定义3个核心Agent：

#### Agent 1：一线客服 Agent

```python
from crewai import Agent

frontline_agent = Agent(
    role="一线IT客服代表",
    goal="快速理解用户问题（含截图与语音），给出准确的解决方案或正确路由",
    backstory="""你是一名经验丰富的企业IT服务台客服，熟悉VPN、密码重置、
    软件安装、报销系统等常见问题。你态度友好，善于用简洁的语言解释技术问题。
    你能看懂用户上传的报错截图，并在多模态知识库中检索文本与图片方案。
    当问题超出你的能力范围时，你会准确地转交给工单处理专家或建议转人工。""",
    tools=[multimodal_search_tool, analyze_screenshot_tool,
           query_ticket_tool, list_user_tickets_tool],
    verbose=True,
    allow_delegation=True,  # 允许委派给其他Agent
    max_iter=5
)
```

**职责**：接收用户消息，进行意图识别和问题分类，调用RAG知识库检索答案，简单问题直接回复，复杂问题则在本轮回复末尾以 `[ESCALATE: yes]` 表态（交由工单 Agent 按需跟进）或触发转人工。

#### Agent 2：工单处理 Agent

```python
ticket_agent = Agent(
    role="IT工单处理专家",
    goal="根据用户需求创建、查询和更新IT服务工单",
    backstory="""你是IT服务台的工单处理专家，负责将用户的问题转化为标准化工单。
    你熟悉工单的优先级判定、分类标准和SLA规则。你能判断什么情况下需要
    创建新工单、什么情况下更新已有工单。""",
    tools=[create_ticket, query_ticket, list_user_tickets,
           update_ticket_status, reset_password, request_software_access],
    verbose=True,
    allow_delegation=False
)
```

**职责**：接收一线客服委派的任务，调用MCP工具完成工单创建、密码重置、权限申请等操作。

**按需触发**：工单 Agent **不是每轮都跑**——只有一线客服在本轮输出末尾以 `[ESCALATE: yes]` 表态（问题无法即时解决 / 用户明确要求线下跟进 / 需密码重置、权限申请）时才另起一轮执行；`[ESCALATE: no]` 时整轮跳过，省掉一次完整的 LLM 往返。标记缺失按 `yes` 保守处理（宁可多跑一次，也不漏建单）。实现见 4.2。

#### Agent 3：质检 Agent（教学演示用，默认关闭）

```python
qa_agent = Agent(
    role="服务质检专员",
    goal="审查AI回复的质量，确保准确、专业、无幻觉",
    backstory="""你是客服质检专员，负责检查AI客服的回复是否准确、
    是否引用了正确的知识库内容、是否存在编造信息的情况。
    你的审查结果用于教学分析。""",
    tools=[],
    verbose=True,
    allow_delegation=False
)
```

**职责**：旁路复核一线客服的回复质量（**不拦截、不改写**），输出不超过 80 字的质检意见，供教学分析。

**默认关闭**：质检为旁路复核，开启后每轮会多消耗一次完整 LLM 往返，故 `CREW_QA_ENABLED` 默认 `false`；需要演示质检链路时置 `true`（开启后才会构建质检 Task 并挂载该 Agent，见 4.2）。

### 4.2 Crew编排

**总开关（双路径）**：会话回复走哪条路由 `CREW_ENABLED` 决定——

| 取值 | 回复生成路径 | 特性 |
|---|---|---|
| `false`（默认） | 中台直连 LLM **流式生成**（`session_flow.SessionTurnFlow.generate_reply` → `core/ai/llm.chat_stream`） | 逐字输出、首字快；Agent 不参与回答生成（见 7.7） |
| `true` | CrewAI 多 Agent 编排（`session_flow.SessionTurnFlow.generate_reply` → `crew_agents.run_crew_turn`） | 一线/工单/质检 Agent 协作、Agent 自主调用检索/截图/工单工具；回复同样**逐字流式**（`crew.kickoff_async()` → `CrewStreamingOutput`） |

两条路径都经同一套 WebSocket 流式事件（`bot_stream_delta` → `bot_stream_end`）收尾，**前端无需切换**；CrewAI 路径逐块推送增量，逐字呈现。

**只挂载本轮真正有任务的 Agent**：一线客服每轮都执行；质检按开关决定是否执行；工单按一线表态**按需另起一轮**执行。

```python
from crewai import Crew, Process

# 主回合：一线客服（+ 可选质检）
support_crew = Crew(
    agents=[frontline_agent] + ([qa_agent] if CREW_QA_ENABLED else []),
    tasks=[handle_inquiry_task] + ([qa_review_task] if CREW_QA_ENABLED else []),
    process=Process.sequential,  # 顺序执行，降低教学复杂度
    verbose=True,
    memory=False,  # 多轮上下文由中台注入任务描述（见 4.5），不用 CrewAI 内置记忆以免与 ChromaDB 冲突
    max_rpm=10     # 限制请求频率，避免API超限
)

# 工单回合：仅当一线输出末尾 [ESCALATE: yes] 时才另起一轮
if escalate:
    ticket_crew = Crew(
        agents=[ticket_agent],
        tasks=[process_ticket_task],
        process=Process.sequential,
        verbose=True,
        memory=False,
        max_rpm=10,
    )
```

### 4.3 MCP Tool 转 CrewAI Tool

中台通过MCP Client连接工单MCP Server，将MCP Tools动态注册为CrewAI Tools：

```python
# core/ai/crew_tools.py
from crewai.tools import BaseTool
from pydantic import BaseModel, Field

class MCPTool(BaseTool):
    """把工单 MCP Server 的一个 Tool 包装成 CrewAI Tool。"""

    name: str = "mcp_tool"
    description: str = ""
    args_schema: Type[BaseModel] = BaseModel
    tool_name: str = ""                      # MCP Server 侧的原始工具名
    recorder: Any = Field(default=None, exclude=True)   # 本轮记录器（写 tool_calls）

    def _run(self, **kwargs) -> str:
        # 同步 Tool 跑在 worker 线程，经 bridge 投回主循环执行（见 5.4）
        return bridge.call_tool_sync(self.tool_name, kwargs)


def build_mcp_tools(recorder, names: list[str] | None = None) -> list[BaseTool]:
    """按 MCP Server 暴露的 schema 动态注册工单工具。

    names=None 注册全部；否则只注册指定工具（见下方两个 Agent 的裁剪）。
    入参模型由 inputSchema 动态生成（_args_model_from_schema）。
    """
    tools = []
    for schema in bridge.tool_schemas():
        tool_name = schema.get("name", "")
        if not tool_name or (names is not None and tool_name not in names):
            continue
        tools.append(MCPTool(
            name=tool_name,
            description=schema.get("description", ""),
            args_schema=_args_model_from_schema(tool_name, schema.get("inputSchema", {})),
            tool_name=tool_name,
            recorder=recorder,
        ))
    return tools
```

### 4.4 多模态诊断工具（进程内 Tool）

多模态检索与截图分析**以进程内 CrewAI Tool 的形式接入**，不额外起 MCP Server。原因：

- 知识检索是**中台内部能力**，不是外部系统（外部系统仍然只有工单系统，见 3.2）
- 保留 Agent **自主决定**是否检索、用什么词检索的能力，且每次调用都写入 `tool_calls`（满足第十五章“全程可旁观”验收项）
- 相比独立 MCP Server，少一个进程与一层协议，演示链路更短

```python
# core/ai/crew_tools.py（进程内 Tool，不走 MCP）

class MultimodalSearchTool(BaseTool):
    """多模态知识库检索：文本与图片共用统一向量空间"""
    name: str = "multimodal_search"
    description: str = """在知识库中检索IT问题解决方案，支持文字与图片两种查询方式。
    用户提供报错截图时，用 image_path 做图查文（找相关文本与相似截图）；
    用户用文字描述问题时，用 query 做文查文/文查图。"""

    def _run(self, query: str = None, image_path: str = None) -> str:
        results = asyncio.run(
            multimodal_rag.search(
                query=query,
                query_image=open(image_path, "rb").read() if image_path else None
            )
        )
        return multimodal_rag.format_results(results)


class ScreenshotAnalyzeTool(BaseTool):
    """截图分析：复用 core/rag/multimodal.py 的 OCR + 视觉理解（见 8.2），不重复建设"""
    name: str = "analyze_screenshot"
    description: str = """分析用户上传的错误截图，提取错误码、错误信息与
    截图中的配置参数，并判断错误类型（网络/权限/软件/系统）。"""

    def _run(self, image_path: str) -> str:
        result = asyncio.run(process_image(open(image_path, "rb").read()))
        return json.dumps(result, ensure_ascii=False)
```

### 4.5 完整对话流程（多模态版）

> 性能优化与工具调用：进入 CrewAI 前，中台只做**预分析截图**（`process_image`），以「【系统预分析（截图，已由视觉模型完成，请勿重复分析）】」注入任务描述，一线 Agent 直接采用、不重复调用 `analyze_screenshot`（省一次 LLM 往返）。**知识库检索不再预跑**，改由一线 Agent 自己调用 `multimodal_search` 完成，避免对同一问题重复检索一次；**仅当 Agent 确实调用了该工具**（命中写回 `recorder`）时，中台才装配参考来源/图片附件/置信度。若 Agent 本轮未调用工具，中台在回合结束后补一次**兜底检索**，但**只用于置信度护栏**、不追加进正文——避免出现「正文在无知识上下文下生成、末尾却挂着兜底检索的引用」这种答非所问的错配（直连路径不受此影响，其预检索结果已注入提示词、属于有据可依）。

```text
用户：发来一张 Nginx 502 报错截图 + 文字“这个怎么解决”
  │
  ▼
Web Chat → 中台会话路由（mode=bot）
  │
  ├─→ 预分析截图：process_image → 【系统预分析（截图）】
  │     {"error_code": "502", "service": "nginx",
  │      "ocr_text": "502 Bad Gateway nginx/1.24.0",
  │      "hint": "upstream timeout"}
  │
  ▼
一线客服Agent接收任务描述（含截图预分析结果；不含预检索，检索由 Agent 自主完成）
  │
  ├─→ 直接采用预分析结论，不再重复调用 analyze_screenshot
  ├─→ 自行调用 multimodal_search（query="Nginx 502 upstream timeout"）检索知识库
  │     ├── 文本块命中：nginx_502.md（排查手册）
  │     ├── 图像块命中：upstream_config.png（配置截图）
  │     └── 精排后返回 top3
  │
  ├─→ Agent生成回复（正文 + 图片附件，图片以配图描述文本参与生成，见 7.7）：
  │     “根据截图，这是 Nginx 上游服务超时导致的 502。
  │      请按以下步骤排查：
  │      1. 检查上游服务是否正常运行
  │      2. 检查 proxy_read_timeout 配置
  │      3. 查看上游服务延迟是否超过阈值
  │      [附：upstream 配置截图]
  │      参考来源：nginx_502.md（第2页）”
  │
  ├─→ 中台装配 citations（来源文件 + 页码）与 attachments（图片块）
  │     ——仅当本轮答案确有检索依据（直连路径的预检索 / Crew 路径 Agent 工具命中）时才装配；
  │       若 Agent 未调用工具，则正文不挂参考来源、不落 confidence（兜底检索只喂护栏）
  │
用户：还是不行，帮我找人处理
  │
  ▼
一线客服Agent判断：知识库无法解决 → 输出 [ESCALATE: yes]
  │
  ▼
工单Agent（按需另起一轮）调用MCP Tool: query_ticket（查是否有相关工单）
  │     返回：无相关工单
  │
  ├─→ 工单Agent调用MCP Tool: create_ticket（自动创建工单）
  │     返回：TICKET-a1b2c3d4
  │
  ▼
质检Agent审查回复质量（仅 CREW_QA_ENABLED=true 时；默认关闭）
  │
  ▼
中台返回回复给用户（含 attachments 图片附件与 citations 参考来源）
```

> **实现口径（双路径，由 `CREW_ENABLED` 切换，见 4.2）**：
> - **默认（`false`）**：最终自然语言回复由中台**直连 LLM 流式生成**（`core/ai/llm.chat_stream`），经 WebSocket 逐块推送（`bot_stream_delta` → `bot_stream_end`，见 7.7 / 10.1）；用户可在等待期点「停止」中断本轮（见 12.3）。此路径下 Agent 编排（工单 / 权限等工具的自主调用、质检）不参与回答生成，转人工后的建单仍由中台按规则触发（见 6.3 / 6.8）。
> - **开启（`true`）**：回复改由 CrewAI 多 Agent 编排产出（`crew_agents.run_crew_turn`），一线 Agent 自主调用检索/截图/工单工具，工单 Agent 按 `[ESCALATE: yes]` 按需建单，质检旁路复核；回复经 `crew.kickoff_async()` **逐字流式**推送（同样走 `bot_stream_delta` → `bot_stream_end`）。



## 五、MCP Server设计

### 5.1 为什么选MCP

| 维度 | 传统REST API | MCP协议 |
|---|---|---|
| 工具发现 | 需手动编码 | 自动发现（list_tools） |
| 调用方式 | 自定义 | 标准化（call_tool） |
| 教学价值 | 低 | 高（协议设计、Server/Client架构） |

### 5.5 工单生命周期与处理规则

工单是本项目唯一的外部业务对象，必须形成“建单 → 跟踪 → 关闭”的完整闭环。状态流转如下：

```text
open(待受理) → in_progress(处理中) → resolved(已解决) → closed(已关闭)
```

**状态推进规则**（演示项目不引入“二线工程师”角色，工单仅作为记录，状态由 AI/坐席按用户确认手动推进）：

| 环节 | 推进方 | 触发条件 |
|---|---|---|
| 创建工单（open） | AI（bot 模式自动）/ 坐席（人工服务中手动） | 问题无法即时解决、需线下跟进；或坐席离线兜底；或用户结束会话时问题未解决（见 6.9） |
| 转处理中（in_progress） | AI / 坐席 | 已有工单且正在跟进该问题 |
| 标记已解决（resolved） | AI / 坐席 | 用户明确确认问题已解决 |
| 关闭（closed） | AI / 坐席 | 工单已 resolved 且用户确认无需继续跟进 |

**建单参数判定规则**（AI 自动建单与坐席手动建单共用，由工单 Agent 依据会话内容与检索结果判定，调用 `create_ticket` 时传入）：

| 维度 | 取值 | 判定标准 |
|---|---|---|
| priority | `high` | 多人受影响 / 核心系统整体不可用 / 用户明确要求加急（如“整个部门都连不上 VPN”） |
| | `medium`（默认） | 单人问题、影响工作但存在绕过方式（如个人 VPN 账号异常、软件安装申请） |
| | `low` | 咨询类、体验优化、不阻塞工作（如界面显示异常、功能使用咨询） |
| category | `network` | 网络 / VPN / 上网 |
| | `password` | 密码重置 / 账号权限 / 登录 |
| | `software` | 软件安装 / 授权 / 报错 |
| | `finance` | 报销 / 财务系统 |
| | `email` | 邮箱 / 邮件收发 |
| | `general`（默认） | 无法归入上述分类 |

> 判定口径：`category` 与知识库文档分类（见 7.6）使用**同一套枚举值**，便于“工单分类 → 知识库检索”双向对齐；Agent 无法确定时使用默认值 `medium` / `general`，并在 `description` 中记录判定依据。

**两种 closed 的关系**：工单 `closed` 与会话 `closed`（见 6.9）是**两套相互独立的状态**——会话关闭不代表工单关闭（用户结束会话后工单可仍在跟进），工单关闭也不要求会话关闭。二者仅通过 `conversation_id` / `user_id` 关联，**不做级联**。

> 说明：`tickets.user_id` 记录发起工单的用户，`tickets.status` 由中台的 AI/坐席代为推进。用户可通过用户端“我的工单”查看自己工单的状态与历史；坐席端在会话中可查看相关工单；管理员可通过管理端“工单管理”（筛选/分页/详情/状态流转）直接读写工单，亦可在对话日志与工具调用日志中观察到工单的创建与状态变更。此规则保证在小规模演示中，工单闭环可被完整走通、可被学员直观观察。

### 5.6 工单与用户体系的标识映射

工单系统是外部系统，其 `user_id` 使用中台用户的 `users.id`（登录时由中台透传），无需在 MCP Server 侧单独维护用户表，避免两套用户体系不一致。


## 六、人工坐席设计

### 6.1 设计原则

人工坐席**不做成MCP Server**，而是中台内置的**会话路由 + 独立的坐席端（/agent）**。原因：人工坐席的本质是**会话控制流的转移**，不是工具调用。硬做成MCP反而会让学员混淆“什么时候该用MCP”。

### 6.2 会话状态机

```text
┌─────────┐   触发转人工   ┌──────────────┐   坐席接入   ┌──────────┐
│  AI模式  │ ───────────→ │ 等待人工排队  │ ─────────→ │ 人工模式  │
│  bot    │              │ waiting_human│            │  human   │
└─────────┘              └──────────────┘            └──────────┘
     ▲                                                      │
     │                    问题解决/坐席释放                   │
     └──────────────────────────────────────────────────────┘
```

### 6.3 转人工触发条件

| 触发条件 | 判断方式 | 对应教学点 |
|---|---|---|
| 用户明确要求 | 关键词命中“转人工”，零 LLM 短路 | 意图分类 |
| 情绪激动 | 情绪识别为愤怒/焦急，持续2轮以上 | 多模态情绪识别 |
| AI置信度低 | 本轮**确实检索到内容** 且 **LLM 判定为 IT 问题**，且 top1 重排分低于阈值 | 置信度护栏 |
| 连续未解决 | 同一问题连续3轮未命中知识库（**只统计 IT 问题轮次**，寒暄/无关话题打断计数） | 对话状态管理 |

### 6.3.1 意图分流（三层，成本从低到高）

用户消息进入后的路由分三层，**每层都不增加 LLM 往返次数**：

| 层 | 判定方式 | 处理 |
|---|---|---|
| 1 | 转人工关键词命中（纯字符串） | 零 LLM 直接转接（实测用户端 0.04s 收到「正在转接」） |
| 2 | 显式寒暄关键词命中（纯字符串） | 免 LLM 分类，直接一句短回复 |
| 3 | 其余 → `perceive_message()` | **一次** LLM 调用同时产出「来意 intent」与「情绪 emotion」 |

第 3 层是复用了原本就存在的情绪识别调用（见 8.2），把它的职责从“只判情绪”扩为“判来意 + 判情绪”，因此**非转人工消息的 LLM 往返次数与改造前完全一致**。

`intent` 取值为 `chitchat | it_issue | off_topic`：

| intent | 处理 |
|---|---|
| `chitchat`（寒暄/闲聊） | 用同一次调用产出的 `reply` 直接回复；**不检索知识库、不写 confidence、不进置信度护栏** |
| `off_topic`（与 IT 无关） | 同上，回复引导用户回到 IT 问题 |
| `it_issue`（IT 问题） | 走 RAG 全流程 + 置信度护栏 |

设计要点：
- **为什么必须分流**：寒暄/闲聊的检索分天然趋近 0（实测「你好」top1=0.0076），而置信度护栏的判据是“分数低就转人工”，不区分来意就会把说「你好」的用户转给人工。
- **为什么不让关键词做主力**：寒暄说法无法穷举，关键词只作为第 2 层的**快速预过滤**（命中即省一次 LLM 分类），其余交给模型。
- **失败降级**：LLM 未配置/超时/JSON 解析失败时，`perceive_message` 回退 `intent="it_issue"`（宁可照常检索，也不漏答真实问题），护栏的来意前置条件同时回退到关键词判定 `detect_it_issue()`。
- **可观测**：`intent` 随用户消息落库（`messages.intent`，差量补列），可用于统计误判率。
- **`intent` 同时约束双条件**：不只是「置信度低」（条件 3），「连续未解决」（条件 4）也必须只统计 IT 问题轮次。寒暄/无关话题走短回复路径、不写 `confidence`，若一并计入，闲聊几轮就把计数垫满——叠加会话开场的欢迎语（同样没有 confidence），实测「欢迎语 + 2 轮寒暄」即达 3 轮阈值，导致紧随其后的第一个真实 IT 问题（哪怕答得满分）被直接转人工。因此计数按轮配对读取 `messages.intent`，遇到非 `it_issue` 立即打断，开场的欢迎语因为没有配对的用户消息而天然被排除。

**置信度阈值必须按所用重排模型实测校准**，不能照搬经验值。本机 `Qwen3-VL-Reranker-8B` 实测 top1 分布：命中问答 0.20~0.70、知识库未覆盖的 IT 问题 0.03~0.06、寒暄/闲聊 ≤0.019，故取 `HANDOFF_MIN_CONFIDENCE=0.15`（落在两带之间）。此前沿用 0.7，导致所有已答问题都低于阈值、几乎必然转人工。注意 `confidence` 是**重排分**（`relevance_score`），不是向量余弦相似度。

参考行业实践，转人工应是显式状态，而不是失败后的兜底字符串。触发条件包括：用户主动要求、连续两轮未解决或重复表达、低置信度/多意图冲突、工具连续失败等。行业常见做法是把自动回复的置信度阈值设在 0.7 附近，但**该值依赖具体重排模型的分数分布**：本项目 `Qwen3-VL-Reranker-8B` 的分数整体偏低（命中问答实测 0.20~0.70），照搬 0.7 会把答对的问题也判为低置信度，故按实测校准为 0.15。

```python
async def should_handoff(
    conv_id: str,
    turn_confidence: Optional[float] = None,
    user_text: str = "",
    kb_nonempty: bool = True,
    intent: Optional[str] = None,
) -> tuple[bool, str]:
    """判断是否需要转人工，返回 (是否转人工, 原因)。判定顺序见 6.3。"""
    # 1. 用户明确要求
    if await detect_handoff_intent(user_text):
        return True, "用户明确要求转人工"

    # 2. 情绪持续负面（连续 2 轮以上）
    if await get_negative_rounds(conv_id) >= settings.HANDOFF_NEGATIVE_ROUNDS:
        return True, "用户情绪持续负面"

    # 3. AI 置信度低。三个前置条件缺一不可：
    #    - 知识库非空（空库必然低分而误触发）；
    #    - turn_confidence 非 None，即本轮确实检索到内容（不回退取上一轮分数）；
    #    - 用户确实在问 IT 问题（优先用本轮 LLM 识别的 intent，缺失时回退关键词判定）。
    it_issue = intent == "it_issue" if intent else detect_it_issue(user_text)
    if kb_nonempty and turn_confidence is not None and it_issue:
        if 0 < turn_confidence < settings.HANDOFF_MIN_CONFIDENCE:
            return True, f"知识库检索置信度{turn_confidence:.2f}，低于阈值"

    # 4. 连续未解决（只统计 IT 问题轮次，寒暄/无关话题打断计数，见 get_unresolved_rounds）
    unresolved = await get_unresolved_rounds(conv_id)
    if unresolved >= settings.HANDOFF_UNRESOLVED_ROUNDS:
        return True, f"连续{unresolved}轮未解决"

    return False, ""
```

### 6.5 回归AI模式

坐席处理完后有两种回归方式：

| 方式 | 触发 | 效果 |
|---|---|---|
| 结束人工服务 | 坐席点击“结束会话” | mode切回bot，**会话本身不关闭**（`status` 仍为 active） |
| 主动交还 | 坐席点击“转回AI”并填写说明 | AI收到坐席说明作为上下文 |

> 口径说明：坐席的“结束会话”指**结束本次人工服务**、把控制权交还 AI，属于状态机回归（见 6.2），**不等于关闭会话通道**。会话的关闭只由 6.8 定义的两类事件触发。三个维度互不干扰：`status` 管通道生死、`mode` 管谁在应答、`tickets.status` 管工单闭环。

```python
async def return_to_ai(conversation_id: str, agent_note: str):
    """坐席交还会话给AI"""
    await db.add_message(
        conversation_id,
        role="system",
        content=f"[人工坐席备注] {agent_note}"
    )
    await db.update_conversation(conversation_id, mode="bot")
```

### 6.8 人机协同分支规则

除主流程（转人工 → 接入 → 交还）外，以下分支必须在需求上明确，否则演示时会出现“卡住但无人处理”的场景。本期为**单坐席（agent01）**演示：

| 分支 | 规则 |
|---|---|
| 排队期间用户继续发言 | 允许；消息入库并标记“排队中”，坐席接入后一并可见；AI 静默，仅提示“正在为您转接人工客服” |
| 坐席离线/忙碌兜底 | 无可用坐席时，先立即回「正在为您转接人工客服」再**自动创建工单**（建单含一次分类 LLM，排在用户可见反馈之后），随后提示“当前坐席繁忙”并告知编号，会话回到 bot 模式 |
| 坐席超时未回复 | 超过 5 分钟提醒坐席；再超时自动**转回 AI** 并记录异常 |
| 用户主动关闭会话 | 用户点击“结束会话”/“问题已解决”，会话置 closed 且不再收发消息；前者若问题未解决则**自动建单**（见 6.9） |
| 坐席切换状态 | 切换为“忙碌/离线”后不再接入新会话，其“服务中”会话保留 |

> 单坐席说明：本期不做多坐席争抢、负载均衡与技能路由；接入即独占会话（会话级互斥），避免演示时出现并发分配问题。

### 6.9 会话关闭口径

会话 `status` 从 `active` 变为 `closed`，**只由以下两类事件触发**，避免“什么时候算关闭”在演示中说不清：

| 触发方式 | 判定条件 | `end_reason` | 执行方 |
|---|---|---|---|
| 用户显式结束 | 用户端点击“问题已解决” | `resolved` | 用户 |
| 用户显式结束 | 用户端点击“结束会话” | `user_closed` | 用户 |
| 超时自动关闭 | `last_message_at` 距今超过 **30 分钟** 无新消息 | `unresolved` | 定时任务 |

**明确不触发关闭的情形：**
- 转人工排队中 / 人工服务中，会话保持 `active`（`mode` 变化不影响 `status`）；
- 坐席点击“结束会话”→ 只切 `mode=bot`（见 6.5），不关闭会话；
- 无坐席兜底自动建工单 → 会话保持 `bot` 模式继续服务，不关闭。

**关闭时的工单处理**（与会话关闭解耦，工单状态口径见 5.5）：

| `end_reason` | 是否建单 | 说明 |
|---|---|---|
| `resolved` | 不建单 | 用户已确认问题解决，无遗留问题 |
| `user_closed` | **建单（open）** | 用户主动结束但问题未解决：若该会话无关联工单，则用会话摘要自动建单（`priority` / `category` 按 5.5 规则判定）并向用户回执工单号；已有工单则不重复建单 |
| `unresolved`（超时） | 不建单 | 超时属静默失联，批量建单会产生僵尸工单；仅在看板计入未解决 |

> 会话关闭**不级联**工单状态：`user_closed` 建的工单保持 `open` 由 AI/坐席后续跟进，不随会话关闭而关闭。

**相关落库规则：**
- 关闭时写入 `ended_at = now()` 与对应 `end_reason`；`resolved` / `unresolved` 用于数据看板的解决率口径（见 11.3）。
- 超时关闭由定时任务批量执行：`UPDATE conversations SET status='closed', end_reason='unresolved', ended_at=now() WHERE status='active' AND last_message_at < now()-30min`；`last_message_at` 为空的会话以 `started_at` 兜底。
- 关闭后不再接受新消息（WebSocket 侧拒绝写入），历史消息仍可读。


## 七、多模态RAG知识库设计

### 7.1 为什么需要多模态 RAG

IT 服务台知识库的真实模态分布如下，近一半知识是图片或表格，纯文本 RAG 会丢掉或扭曲这些信息：

| 模态 | 占比 | 纯文本 RAG 的处理方式 |
|---|---|---|
| 纯文本（操作手册、FAQ） | 55% | 直接嵌入 ✅ |
| 图片（报错截图、拓扑图、流程图） | 22% | 丢弃，或 OCR 成文字（丢失视觉信息） |
| 表格（配置表、错误码表） | 15% | OCR 成乱序文字，行列关系丢失 |
| PDF 扫描件 | 8% | OCR，版面结构丢失 |

具体到本项目的三个场景：

1. **用户发来的报错截图**：识别文字 + 判断错误类型，结合知识库中的配置文档给出方案。
2. **知识库中的配置表与拓扑图**：纯文本 RAG 丢失的图片/表格信息，可被直接检索到并作为图片附件回复给用户。
3. **语音描述的模糊问题**：ASR 转文字后，结合检索进行多轮引导式诊断。

### 7.2 多模态嵌入方案（核心决策：文本优先）

本项目采用**单一多模态嵌入模型** `Qwen/Qwen3-VL-Embedding-8B`（硅基流动在线 API）作为**文本编码器**，
但入库索引的内容**一律是文本**：

- 文本块 → 原文直接 `encode_text`；
- 表格块 → 结构化为 Markdown 后 `encode_text`；
- **图片块 → 入库期由 VLM 生成「配图描述」→ `encode_text`**（图片本身不进向量库，仅落盘 `data/media`，靠 `asset_id` 关联、命中后作附件回传）；
- 用户上传截图查询 → 先由 VLM 生成描述 → 再 `encode_text` 检索。

因此向量库里只有**一个集合、一个维度**的文本向量，不存在跨模态对齐问题；
"文查图"由「文本 → 图片描述」的语义匹配承担，原图精确匹配（以图搜图）降级为语义匹配
（缺陷复盘与决策记录见[多模态 RAG 文本优先改造方案](./多模态%20RAG%20文本优先改造方案.md)）。

| 对比项 | 传统做法（BGE 文本 + CLIP/ColPali 图像） | 本项目（文本优先：图片只索引描述） |
|---|---|---|
| 向量空间 | 多空间，需跨空间融合 | **单文本空间**，无融合开销 |
| 跨模态检索 | 依赖 RRF 强行融合异构分数，语义上不成立 | **图 → 描述 → 文本** 语义匹配 |
| 向量库 | 多集合/多向量 | **单集合、单维度** |
| 阈值口径 | 各空间分数分布不同，需分别校准 | **统一一套阈值** |
| 精确细节（如表格数字） | 依赖 OCR | 由 **精排模型** 补偿 |

配套使用 `Qwen/Qwen3-VL-Reranker-8B` 做**召回后精排**，形成“召回 → 精排”两段式检索。

> **为什么单空间不需要 RRF**：RRF 的作用是融合**打分口径不同的多路结果**。文本优先后，全库都是文本向量、同一度量，可直接比较排序。若后续需要补充 BM25 关键词召回，可对“向量排名 + 关键词排名”再做 RRF（属于同口径融合，可选，演示默认关闭）。

### 7.3 知识库流程

```text
【入库】
文档 / 截图上传 → 解析（文本提取 + 图片抽取 + 表格结构化）
    ├── 文本块 → encode_text ───────────────────────────┐
    ├── 图片块 → VLM 配图描述 → encode_text ─────────────┼→ 单一文本向量空间（同维度）
    └── 表格块 → 结构化为 Markdown → encode_text ────────┘
                       │
              ChromaDB 单集合（metadata: modality = text/image/table；
                              image 另带 caption 与 asset_id）

【检索】
用户提问（文字 / 截图 / 语音）
    ├── 文字 → encode_text
    ├── 截图 → VLM 生成描述 → encode_text（图→文 语义匹配）
    └── 语音 → ASR 转文字 → encode_text
                       │
              向量召回 top_k=10（单集合，一次查询覆盖全部模态）
                       │
              Qwen3-VL-Reranker-8B 精排 → 取 top_n=3 → 送入 LLM
```

### 7.4 核心实现

```python
# core/rag/multimodal_rag.py
class MultimodalRAGService:
    """
    文本优先的多模态 RAG：
      - 文本 / 表格 Markdown / 图片配图描述 全部走 encode_text 进同一文本空间
      - 单集合、单维度（EMBEDDING_DIM）；图片不直接嵌入，命中后由 build_attachments 回传原图
      - 召回后用 Qwen3-VL-Reranker-8B 精排
    """

    def __init__(self, embedder, reranker, vector_store):
        self.embedder = embedder          # Qwen3-VL-Embedding-8B（在线 API）
        self.reranker = reranker          # Qwen3-VL-Reranker-8B（可关闭）
        self.vector_store = vector_store  # ChromaDB（单集合）

    async def add_document(self, file_path: str, category: str = "general"):
        """文档入库：解析 → 分块（文本/图片/表格）→ 文本优先嵌入 → 落库"""
        pages = await self._parse_document(file_path)

        for page in pages:
            # 1. 文本块
            for chunk in self._chunk_text(page.text, chunk_size=500, overlap=50):
                emb = await self.embedder.encode_text(chunk)
                self.vector_store.add(emb, {
                    "modality": "text", "content": chunk,
                    "source": file_path, "category": category, "page": page.no
                })

            # 2. 图片块（降采样落盘取 asset_id，用 VLM 配图描述按文本嵌入；
            #    原图不参与检索，命中后由 build_attachments 作附件回传）
            for img in page.images:
                data, ext = downsample(img.data, settings.EMBEDDING_MAX_IMAGE_SIDE,
                                       settings.EMBEDDING_MAX_IMAGE_BYTES)
                asset_id = save_media(data, ext, prefix="kb")
                caption = await describe_knowledge_image(data)
                emb = await self.embedder.encode_text(caption or self._find_context(img, page.text))
                self.vector_store.add(emb, {
                    "modality": "image", "asset_id": asset_id, "caption": caption,
                    "context": self._find_context(img, page.text),
                    "source": file_path, "page": page.no
                })

            # 3. 表格块（结构化为 Markdown 后按文本嵌入，保住行列关系）
            for table in page.tables:
                md = self._table_to_markdown(table)
                emb = await self.embedder.encode_text(md)
                self.vector_store.add(emb, {
                    "modality": "table", "content": md,
                    "source": file_path, "page": page.no
                })

    async def search(self, query: str = None, query_image: bytes = None,
                     top_k: int = 10) -> list:
        """多模态检索（单集合、文本优先）：召回 → 精排"""
        if query_image:                                          # 图查文：先由 VLM 生成描述
            query = await describe_knowledge_image(query_image)
            if not query:
                return []
        vec = await self.embedder.encode_text(query or "")
        candidates = self.vector_store.search(vec, top_k=top_k)  # 单集合，天然跨模态

        if self.reranker.enabled and query:                      # 精排需要文本 query
            return await self.reranker.rerank(query, candidates,
                                              top_n=settings.RERANKER_TOP_N)
        return candidates[:settings.RERANKER_TOP_N]

    def format_results(self, results: list) -> str:
        """把检索结果拼成带来源标注的上下文：text 取正文、table 取 Markdown、image 取配图描述（回退上下文文字）"""
        blocks = []
        for i, r in enumerate(results, 1):
            m = r.metadata
            body = m.get("content") or m.get("caption") or m.get("context", "")
            blocks.append(f"[{i}] 来源：{m['source']}（第{m.get('page', '-')}页·{m['modality']}）\n{body}")
        return "\n\n".join(blocks)

    def build_attachments(self, results: list) -> list:
        """把检索命中的图像块转为消息附件：原图经鉴权媒体接口回传，
        生成期改用配图描述文本（文本优先，口径见 7.7）"""
        return [{"type": "image", "url": f"/api/media/{r.metadata['asset_id']}",
                 "source": r.metadata["source"], "page": r.metadata.get("page"),
                 "caption": r.metadata.get("caption", "")}
                for r in results if r.metadata.get("modality") == "image"]

```

> **注意（准入门槛未启用）**：`RETRIEVAL_MIN_SCORE` **当前未接入检索流程**（`search()` 不据此过滤），仅作预留配置。历史上曾评估在**精排分**上加准入闸门（口径正确：阈值须作用于精排分而非向量余弦分，并按具体精排模型实测分布校准，不可照搬其他模型的 0.7）。本项目实测（Qwen3-VL-Reranker-8B）：无关提问 top1 ≈ 0.001~0.004，相关提问 top1 ≈ 0.023~0.887——分离虽干净，但按 0.5 加闸门会误杀大量相关命中（实测相关召回 10/10 → 3/10），故**决定不加闸门**，转而由**精排分驱动的转人工护栏**（`HANDOFF_MIN_CONFIDENCE`，见 6.3）兜底低置信度场景。

### 7.6 知识库管理需求

知识库由 **admin** 在 `/admin/knowledge` 维护（权限见 11.3）。演示项目采用**最小可用集**：

| 维度 | 规则 |
|---|---|
| 支持格式 | `md` / `txt` / `pdf` / `docx`（解析库提取文本），以及 `png` / `jpg` / `jpeg`（直接作为图像块入库） |
| 单文件大小 | ≤ 10 MB |
| 文档数量 | ≤ 50 篇（演示量级，超出提示先清理） |
| 多模态入库 | pdf/docx 中的**图片**抽取为图像块、**表格**结构化为表格块，二者**统一转为文本**（图片由 VLM 生成配图描述）后与文本块**进入同一文本向量空间**；图片入库前按 `EMBEDDING_MAX_IMAGE_SIDE` 降采样以控制成本 |
| 上传方式 | 通过管理端上传，**上传即索引**（解析 → 分块 → 嵌入） |
| 在线编辑 | **不提供**富文本编辑，仅支持 上传 / 删除 / 查看分块内容 |
| 分类 | 上传时填写 `category` 标签，取值与工单分类**共用同一套枚举**（network/password/software/finance/email/general，见 5.5），用于列表筛选与“工单 → 知识库”对齐 |
| 审核流 | **不做审核**（演示项目无审批角色，上传即生效） |
| 删除一致性 | 删除文档时**级联删除其全部向量**，避免检索到“幽灵分块” |
| 重建索引 | 提供 `[重建索引]` 全量重跑（**换嵌入模型或改维度后必须执行**） |
| 检索测试 | 提供 `[测试检索]`，支持 **纯文本模式 vs 多模态模式** 对比，展示命中模态、相似度与分块内容 |

### 7.7 检索结果到回复生成

检索拿到 `top_n=3` 后**直接生成**（不再做检索准入门槛过滤，`RETRIEVAL_MIN_SCORE` 未接入，见 7.4 注意；低置信度场景由转人工护栏兜底，见 6.3）。回复生成有**两套路径**（由 `CREW_ENABLED` 切换，见 4.2），全链路如下：

```text
search() → top_n=3
  │
  ▼
① format_results：text 取正文、table 取 Markdown、image 取配图描述（回退上下文文字） → 带来源标注的上下文
② 组装生成输入：上下文（含图片配图描述）+ 截图预分析文字 → 产出回复正文
     ├─ CREW_ENABLED=false（默认）：中台直连 LLM **流式生成**（逐 token 产出）
     └─ CREW_ENABLED=true：CrewAI 一线 Agent 编排生成（同样逐字流式，必要时自主调用工具）
③ 正文末尾追加“参考来源”（来源文件 + 页码 + 模态）
④ 命中图片装配为 attachments（见 8.4）
⑤ [仅 CrewAI 路径] 质检 Agent 复核（旁路记录，不拦截、不改写；需 CREW_QA_ENABLED=true，见 4.1）
⑥ 落库 messages → WebSocket 流式推送：bot_stream_delta → bot_stream_end（见 10.1）
```

> **流式生成**：默认路径下，检索与截图预分析完成后，「最终自然语言回答」由中台经 OpenAI 兼容协议**直连 LLM 流式生成**（`core/ai/llm.chat_stream`），逐块经 WebSocket 推送给前端（`bot_stream_delta`），收尾时 `bot_stream_end` 携带含“参考来源”的定稿正文与附件。这样学员在等待检索（数秒）后即可看到文字**逐字浮现**，而不是继续干等完整答案；若改走 CrewAI 编排（`CREW_ENABLED=true`），则换来 Agent 自主调用检索/工单等工具的能力，回复同样经 `crew.kickoff_async()` **逐字流式**输出。

**① 结果 → 上下文**：三种块取的字段不同，且每条都带 `[序号] 来源：文件（第 N 页·模态）` 前缀，既供模型引用、也供前端展示来源（实现见 7.4 `format_results`）。

| 块类型 | 拼入上下文的内容 |
|---|---|
| `text` | `metadata.content` 原文 |
| `table` | `metadata.content`（已结构化为 Markdown，行列关系保留） |
| `image` | 优先 `metadata.caption`（配图描述）、回退 `metadata.context`（插图所在段落文字） |

**② 生成输入（文本优先）**：生成模型是**纯文本输入**——命中图片块的**配图描述文本**已随 `format_results` 拼进上下文（见①），用户上传截图则由 `process_image` 预分析为文字提示（`screenshot_hint`）注入；模型据此"读懂"图片，而非直接接收图像字节。约束：

- 图片只在**入库期**经 VLM 生成配图描述（`VLM_MODEL`，见 17.2），生成期不再喂原图，故 `LLM_MODEL` 无需视觉能力；
- 命中整页大图（扫描页，同属 `image` 模态）时取其配图描述文本，避免上下文过长；
- 命中图片的**原图**仍作为 `attachments` 回传前端展示（见 8.4），供用户查看，不参与生成。

**③ 来源引用（显示）**：回复正文末尾追加"参考来源"小节，列出本次实际使用的 `source` 与 `page`，前端以灰色小字/可折叠列表渲染（字段见 10.1 `citations`，展示见 12.3）。规则：

| 情况 | 来源引用行为 |
|---|---|
| 正常命中 | 列出全部送入生成的来源（文件 + 页码 + 模态） |
| 命中后被精排截断 | 只列 `top_n` 内实际使用的来源，不列已丢弃的候选 |
| 未命中 / 转人工 | **不显示**（避免出现"无来源"的空引用） |
| 坐席人工回复 | 不显示（非 RAG 生成） |

### 8.4 多模态输出：图片回复

多模态检索会命中**图像块/表格块**（报错截图、拓扑图、配置图）。若回复不能带图，用户看不到检索价值，多模态演示即失去意义。因此 AI 回复支持携带**图片附件**：

```python
# core/rag/multimodal_rag.py —— MultimodalRAGService 的方法（同步，非 async）
def build_attachments(self, results: list[dict]) -> list[dict]:
    """把检索命中的图像块转为消息附件（写入 messages.attachments）"""
    attachments = []
    for result in results:
        metadata = result.get("metadata") or {}
        if metadata.get("modality") != "image" or not metadata.get("asset_id"):
            continue
        attachments.append({
            "type": "image",
            "url": f"/api/media/{metadata['asset_id']}",   # 经鉴权的媒体接口
            "source": metadata.get("source"),
            "page": metadata.get("page"),
            "caption": metadata.get("caption") or "",      # 入库期由 VLM 生成的配图描述
        })
    return attachments
```

| 要点 | 说明 |
|---|---|
| 消息载体 | `bot_reply` 的 `data.attachments` 数组（见 10.1），落库到 `messages.attachments` |
| 前端渲染 | 气泡内缩略图，点击放大（见 12.3） |
| 来源引用 | AI 回复正文末尾附“参考来源”（来源文件 + 页码 + 模态），随 `citations` 字段下发；坐席人工回复不附（见 7.7） |
| 存储与访问 | 图片存本地 `data/media/`，经 `/api/media/{id}` 鉴权访问，**不裸露静态路径** |
| 边界 | 本项目**不做数字人（口型/表情/视频播报）**，仅做文本 + 语音 + 图片附件 |

### 10.1 消息格式

```json
{
    "type": "message | handoff | agent_message | system",
    "conversation_id": "conv-xxx",
    "data": {
        "role": "user | assistant | agent | system",
        "content": "消息内容",
        "modality": "text | voice | image",
        "attachments": [
            {"type": "image", "url": "/api/media/img-xxx", "source": "vpn_error_619.png", "page": 3, "caption": "VPN 客户端报错 619 的截图"}
        ],
        "citations": [
            {"source": "vpn.md", "page": 3, "modality": "text"},
            {"source": "error_code_table.md", "page": 1, "modality": "table"}
        ],
        "emotion": "positive | neutral | negative",
        "timestamp": "2026-10-01T10:00:00Z"
    }
}
```

> `attachments` 用于承载图片等附件：用户上传的截图回显、AI 检索命中的图像块回复（见 8.4）均通过该字段传递；无附件时为空数组或省略。
>
> `citations` 用于承载“参考来源”：仅 AI（RAG）回复携带，列出本次生成实际使用的知识来源（见 7.7）；坐席人工回复、转人工与未命中场景为空数组或省略。

**流式回复（见 10.2）**：AI 回复不再一次性下发，而是拆成多帧增量推送，便于前端边收边渲染、避免长等待：

```text
Server → Client  {"type":"bot_stream_delta","conversation_id":"conv-xxx","data":{"delta":"根据截图，"}}
Server → Client  {"type":"bot_stream_delta","conversation_id":"conv-xxx","data":{"delta":"这是 Nginx 上游超时"}}
...
Server → Client  {"type":"bot_stream_end","conversation_id":"conv-xxx",
                  "data":{"role":"assistant","content":"<完整正文（含参考来源）>",
                          "attachments":[...],"citations":[...],"timestamp":"..."}}
```

- `bot_stream_delta` 只携带增量 `delta`，前端累加到同一条 AI 气泡上；
- `bot_stream_end` 携带**定稿正文**（含“参考来源”小节）与 `attachments`/`citations`，前端据此收尾该气泡；
- 用户点击「停止」时，前端发送 `{"type":"stop","conversation_id":"conv-xxx"}`，服务端取消该会话正在执行的回合并回推 `generation_stopped`，此后**不再有** `bot_stream_delta` / `bot_stream_end`。


### 10.2 关键事件

| 事件类型 | 方向 | 说明 |
|---|---|---|
| `user_message` | Client → Server | 用户发送消息 |
| `stop` | Client → Server | 用户点击「停止」，取消本会话正在执行的 AI 回合（含流式生成） |
| `bot_stream_delta` | Server → Client | AI 流式增量，`data.delta` 为本次新增的正文片段 |
| `bot_stream_end` | Server → Client | AI 流式回复结束，携带定稿正文（含参考来源）、`attachments`、`citations` |
| `generation_stopped` | Server → Client | 已响应「停止」，`data.cancelled` 表示是否确实中断了任务 |
| `bot_reply` | Server → Client | AI 一次性回复（寒暄/无关话题等短回复，非流式路径） |
| `handoff_triggered` | Server → 坐席工作台 | 触发转人工通知 |
| `agent_joined` | Server → Client | 坐席接入通知 |
| `agent_message` | Server → Client | 坐席回复 |
| `return_to_bot` | Server → Client | 回归AI模式 |


## 十一、用户管理与角色管理

### 11.1 设计原则

演示项目不需要企业级RBAC（角色-权限-资源三级模型），只需要**三个业务角色 + 简单权限**。目标是：

- 用户能登录、能聊天、能跟踪自己的工单
- 坐席能登录、能处理转人工
- 管理员能登录、能管知识库、能**只读旁观**全流程

- 坐席为**单坐席（agent01）**演示：排队、负载均衡、多坐席争抢等调度需求大幅简化

### 11.4 认证方式

教学项目用最简单的 **Token + Session** 即可，不需要OAuth2/JWT复杂方案。

```python
# core/infra/auth.py
import hashlib, secrets
from datetime import datetime, timedelta

def hash_password(password: str) -> str:
    return hashlib.sha256(password.encode()).hexdigest()

async def login(username: str, password: str) -> dict:
    user = await db.get_user_by_username(username)
    if not user or user.password_hash != hash_password(password):
        return {"error": "用户名或密码错误"}

    token = secrets.token_urlsafe(32)
    await db.create_session(
        token=token,
        user_id=user.id,
        role=user.role,
        expires_at=datetime.now() + timedelta(hours=8)
    )
    return {
        "token": token,
        "user_id": user.id,
        "role": user.role,
        "display_name": user.display_name
    }

async def get_current_user(token: str) -> dict:
    session = await db.get_session(token)
    if not session or session.expires_at < datetime.now():
        return None
    return await db.get_user(session.user_id)
```

> ⚠️ **安全警示（演示项目专属取舍）**
> 1. 密码采用 `sha256` 直接哈希（**无加盐、无慢哈希**），仅适用于本地演示，**禁止用于生产环境**；生产应替换为 `bcrypt`/`argon2`。
> 2. 演示账号统一使用弱口令 `123456`，**不得部署到公网**；如需外网演示，须先修改初始密码并限制访问来源。
> 3. 账号初始化脚本与知识库播种接口（`/api/auth/init`、`/api/admin/knowledge/seed`）均要求 **admin 鉴权**（账号另在启动时由 lifespan 自动差量补种），不可作为公开 HTTP 端点暴露。

### 11.5 权限校验中间件

```python
# core/infra/middleware.py
from fastapi import Request, HTTPException

def require_role(*allowed_roles):
    """角色校验装饰器"""
    async def checker(request: Request):
        token = request.headers.get("Authorization", "").replace("Bearer ", "")
        user = await get_current_user(token)
        if not user:
            raise HTTPException(401, "未登录")
        if user.role not in allowed_roles:
            raise HTTPException(403, "权限不足")
        request.state.user = user
        return user
    return checker

# 使用示例
@app.get("/api/admin/knowledge")
async def list_knowledge(request: Request):
    await require_role("admin")(request)
    # ... 只有admin能访问

@app.get("/api/agent/queue")
async def get_queue(request: Request):
    await require_role("agent", "admin")(request)
    # ... 坐席和管理员能访问
```

**关键交互：**

1. **模式切换提示**：当会话从bot转到waiting_human，聊天窗口顶部显示黄色横幅“正在为您转接人工客服，请稍候...”；当坐席接入，横幅变为绿色“人工客服已接入”。

2. **消息角色区分**：
   - AI回复：左侧，蓝色头像，标签“AI客服”
   - 坐席回复：左侧，绿色头像，标签“人工客服”
   - 用户消息：右侧
   - 系统消息：居中，灰色小字

3. **多模态输入**：
   - 麦克风按钮：点击开始录音，松开上传
   - 相机按钮：选择图片上传
   - 上传后显示预览，发送后消息气泡内显示图片/音频

4. **会话关闭（只读态）**：用户点击“结束会话”或“问题已解决”后，会话置 `closed` 并记录 `end_reason`（见 6.9）。此时聊天窗口顶部显示提示“该会话已结束，如需继续请新建会话”，**输入框与发送按钮置灰禁用**，历史消息保持可读可滚动；若为“结束会话”且问题未解决，系统自动建单并在窗口内回执工单号（引导用户到“我的工单”跟踪），用户如需继续咨询则点击左侧“+ 新会话”开启新一轮对话。打开一个历史已关闭会话时，同样进入该只读态。

5. **参考来源展示**：AI 回复气泡底部渲染 `citations`（来源文件 + 页码），默认折叠为一行“参考来源 (2)”，点击展开列表；历史会话回看时从 `messages.citations` 还原，口径见 7.7。

6. **流式输出与停止生成**：用户发送消息后，AI 回复以**逐字流式**方式渲染（`bot_stream_delta` 增量累加，光标闪烁；首字到达前显示“思考中”三点）。在 AI 回复期间进入**等待态**：输入框与语音/图片按钮置灰不可输入，输入框提示“AI 正在回复中，可点击「停止」中断…”，右侧按钮由蓝色「发送」变为红色「停止」。点击「停止」即发送 `stop` 消息取消本轮 AI 回合，收到 `generation_stopped` 后复位等待态；已有部分文字保留并标注“已停止生成”，无内容则移除占位气泡。回复结束（`bot_stream_end`）后输入区自动恢复，「停止」复原为「发送」。

### 12.7 WebSocket连接与角色绑定

不同角色连接不同的WebSocket端点：

```javascript
// 前端 src/api/ws.js：与页面同源拼接，不写死 localhost:8000。
// 开发期 Vite devServer 已把 /ws 代理到后端 8000（vite.config.js 中 ws: true），
// 生产由 8000 直接伺服前端产物——两种情形都取当前页面的 host 即可。
export function buildWsUrl(role, token) {
  const protocol = window.location.protocol === 'https:' ? 'wss:' : 'ws:'
  return `${protocol}//${window.location.host}/ws/${role}?token=${encodeURIComponent(token)}`
}

// 用户端 / 坐席端 / 管理端分别连 /ws/user、/ws/agent、/ws/admin
const ws = new WebSocket(buildWsUrl('user', token));   // 'agent' / 'admin' 同理
```

后端根据token解析角色，将连接加入不同的广播组：

```python
# core/infra/ws_manager.py
class WSManager:
    def __init__(self):
        self.user_connections = {}    # user_id -> ws
        self.agent_connections = {}   # agent_id -> ws
        self.admin_connections = []   # admin ws列表

    async def broadcast_to_agents(self, message: dict):
        """广播给所有在线坐席"""
        for ws in self.agent_connections.values():
            await ws.send_json(message)

    async def send_to_user(self, user_id: str, message: dict):
        """发送给指定用户"""
        ws = self.user_connections.get(user_id)
        if ws:
            await ws.send_json(message)
```

| 浏览器兼容 | Chrome / Edge 最新版 | 演示统一使用 Chrome |

## 十七、配置管理

### 17.1 设计原则

所有外部模型与服务通过 **`.env` 环境变量**注入，由 `core/config.py`（pydantic-settings）统一加载。命名以 **“能力四元组”** 为主：

```text
{能力}_PROVIDER / {能力}_BASE_URL / {能力}_MODEL / {能力}_API_KEY
```

**具备完整四元组**的是 LLM / EMBEDDING / ASR / OCR，全部走 **OpenAI 兼容协议**，因此**替换供应商只改变量、不改代码**（例如从硅基流动换成其他在线服务）。少数能力按需要裁剪：

| 能力 | 变量 | 说明 |
|---|---|---|
| VLM | `VLM_BASE_URL` / `VLM_MODEL` / `VLM_API_KEY` | 三元组，无 `_PROVIDER`（固定 OpenAI 兼容） |
| RERANKER | `RERANKER_ENABLED` / `_BASE_URL` / `_MODEL` / `_API_KEY` / `_TOP_N` | 用开关控制启停，无 `_PROVIDER` |
| TTS | `TTS_PROVIDER` / `TTS_VOICE` | 默认本地 `edge`（edge-tts，免费），非 OpenAI 协议 |

### 17.2 .env 配置项


### 17.3 配置要点

| # | 要点 | 说明 |
|---|---|---|
| 1 | **Key 回退** | `{能力}_API_KEY` 留空时继承 `SILICONFLOW_API_KEY`；优先级：`{能力}_API_KEY` > `SILICONFLOW_API_KEY`。硅基流动一个 Key 即可覆盖 LLM / embedding / reranker / VLM |
| 2 | **启动自检（fail-fast）** | 必填项缺失时直接启动失败，报错定位到“哪个能力、哪个变量”；并试调一次 embedding 校验**返回维度 == `EMBEDDING_DIM`**，不匹配则拒绝启动 |
| 3 | **换嵌入模型必须重建索引** | 模型或维度变更后，旧向量与新向量不在同一空间，必须执行 `[重建索引]` |
| 4 | **准入门槛未启用** | `RETRIEVAL_MIN_SCORE` **当前未接入检索流程**（`search()` 不据此过滤），仅作预留配置；如启用须作用于**精排分**并按具体模型实测分布校准（不可照搬其他模型的 0.7，实测 0.5 会误杀大量相关命中，见 7.4） |
| 5 | **密钥治理** | `.env` 加入 `.gitignore`，仓库只保留 `.env.example`（占位值）；模型名一律走变量，不硬编码 |
| 6 | **生成期文本优先** | 生成输入为**纯文本**（命中图片的配图描述 + 截图预分析文字，见 7.7），`LLM_MODEL` 无需视觉能力；视觉能力（截图理解、配图描述）由 `VLM_MODEL` 承担，未配置 VLM 时配图描述跳过、回退页正文 |
| 7 | **回复生成双路径** | `CREW_ENABLED=false`（默认）走中台直连 LLM **逐字流式**；`true` 走 **CrewAI 多 Agent 编排**（Agent 自主调工具，回复同样**逐字流式**）。两条路径共用同一套流式事件，前端无需切换（见 4.2） |

## 十八、部署方案

### 18.1 Docker Compose

容器部署文件统一收敛到 `deploy/`：`Dockerfile.core`（中台）、`Dockerfile.frontend`（前端）
与 `docker-compose.yml`。两个镜像**共用仓库根目录作为构建上下文**（`context: ..`），
前端镜像因此在 Dockerfile 内以 `frontend/` 前缀拷贝源码；`.dockerignore` 位于仓库根目录。

```yaml
# deploy/docker-compose.yml（Compose V2，无需 version 字段）
services:
  core:
    build:
      context: ..                 # 仓库根目录（需拷贝 core / eval / mcp_servers 等）
      dockerfile: deploy/Dockerfile.core
    image: mde-lab-core:1.0.0
    container_name: mde-lab-core
    ports:
      - "8000:8000"
    volumes:
      - ../data:/app/data         # 知识库文件、ChromaDB、媒体文件、业务库均持久化在此卷内
    env_file:
      - ../.env                   # 统一读取配置（见十七章）
    environment:
      TICKETS_DB_PATH: /app/data/tickets.db   # 工单库落在数据卷内，重启不丢
      DB_PATH: /app/data/app.db
      CHROMA_PATH: /app/data/chroma
      MEDIA_DIR: /app/data/media
    restart: unless-stopped
    # 注意：ChromaDB 为嵌入式，core 必须单实例运行，不启用多 worker

  frontend:
    build:
      context: ..
      dockerfile: deploy/Dockerfile.frontend
    image: mde-lab-frontend:1.0.0
    container_name: mde-lab-frontend
    ports:
      - "3000:3000"
    environment:
      BACKEND_TARGET: http://core:8000   # vite preview 代理 /api 与 /ws 到 core
    depends_on:
      - core
    restart: unless-stopped
```

> 与 Qdrant 方案相比，**不再需要独立的向量库容器**；ChromaDB 以嵌入式库形式随 `core` 进程运行，数据落在 `./data/chroma`。

### 18.2 最小启动步骤

```bash
# 1. 克隆项目
git clone <repo-url> && cd mde-lab

# 2. 配置环境变量
cp .env.example .env
# 编辑 .env 填入 SILICONFLOW_API_KEY（或按能力分别填 *_API_KEY；LLM_API_KEY 留空即回退）

# 3. 启动服务（容器部署文件在 deploy/ 下）
docker compose -f deploy/docker-compose.yml up -d

# 4. 演示账号与知识库

# 5. 访问
# 用户端: http://localhost:3000/login
# 演示账号: user01 / user02 / agent01 / admin，密码均为 123456
```


## 十九、总结

本项目是一个**简化但完整**的多模态数字员工平台，核心特点：

1. **真实技术栈**：CrewAI多Agent、MCP协议、多模态RAG、ASR/TTS/OCR、WebSocket全部真实运行。
2. **多模态闭环**：文本优先嵌入（文本/图片配图描述/表格统一进文本空间）→ 精排 → 带图回复，AI 能“看懂截图、找到图片”。
3. **极简外部依赖**：只有一个工单系统MCP Server，其余全部内置（知识检索为进程内 Tool）。
4. **完整人机协同**：AI → 转人工 → 坐席服务 → 回归AI，全流程闭环。
5. **三角色分端**：用户端、坐席端、管理端，权限清晰，统一 Vue SPA 按角色路由。
6. **可按模块演示**：8 个模块，支持按模块分段演示。
7. **一键部署**：Docker Compose 启动（无独立向量库容器），初始化脚本创建演示账号和知识库。

学员通过这个项目，可以掌握多Agent协作、MCP协议、多模态RAG、多模态感知、人机协同、认证授权、分角色前端等企业级AI应用的核心技术，同时理解真实商业场景中的架构设计取舍。
